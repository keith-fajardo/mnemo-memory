# ADR 0026: Live episodic import rebases deterministic identities and verifies the target

- **Status:** accepted
- **Date:** 2026-08-06
- **Deciders:** Mnemo maintainers
- **Issue:** 21R
- **Supersedes:** none
- **Superseded by:** none

## Context

Personal and team episodic storage already share one strict export bundle, but replaying a personal
bundle directly into a team task would retain its personal scope. Several event, review,
governance, and deletion identities are intentionally derived from scope, so changing only a scope
field would also produce invalid objects. Imports may also be interrupted between repository calls
or collide with unrelated target state.

Payload-free expiration and deletion bundles add a separate problem: their source payload is
deliberately absent, while existing PostgreSQL triggers require that payload when first creating a
tombstone. Silently dropping those records would permit resurrection and cannot be called a
successful import.

## Decision

The first import service accepts only an already validated `mnemo.episodic-export.v1` bundle and one
exact target task scope. It reconstructs each live object through its canonical factory in
dependency order: task event, candidate batch, review, then governance action. Scope-derived event,
candidate, review, governance, and revision identities are therefore deterministically rebased;
content, retention, evidence, timestamps, extraction provenance, review decisions, and correction
semantics are retained.

Before mutation, the service exports the target at the same logical time. Existing target objects
must be an exact typed subset of the rebased projection. An unrelated or conflicting object fails
before a write. Replay uses repository idempotency, so an interruption can be retried and converge.
After replay, a second export must be semantically identical to every expected typed object and
have exact category counts. The result reports the independently validated source digest and the
canonical digest generated by the target repository. Equivalent timestamp instants may have
different serialized UTC offsets across SQLite and PostgreSQL, so semantic verification compares
typed datetimes while retaining each backend's own integrity-checked canonical digest.

A bundle containing any memory/source expiration, purge, or deletion tombstone is rejected with a
dedicated unsupported-lifecycle outcome before the target is read or mutated. A following issue
must add one storage-level tombstone path without weakening anti-resurrection triggers.

## Alternatives considered

- **Copy serialized rows and replace only scope.** Rejected because scope-derived identities would
  be invalid and personal IDs could collide with team state.
- **Ignore tombstones and import live records.** Rejected because omitted deletion state could
  resurrect content.
- **Require an empty target.** Rejected because a retried interrupted import needs to resume from
  its exact already-written subset.
- **Add a staging schema now.** Deferred because live repository operations are already idempotent;
  staging is justified only by the lifecycle-tombstone workflow that needs it.

## Consequences

SQLite/reference exports can now populate live PostgreSQL team episodic state with verified counts
and source/target hashes. The operation is resumable rather than one cross-repository transaction;
partial state is never reported as success and must pass the same preflight and final verification
on retry. The full personal-to-team exit gate remains open until lifecycle state and the other
export categories are supported.

## Security and privacy implications

The input bundle validates exact scope, relationships, ordering, and SHA-256 integrity before this
service runs. Every target repository call applies its existing deterministic secret policy and
team RLS before mutation. Storage exceptions are translated to one payload-free outcome. The
service does not log or return claims, evidence locations, identifiers, or adapter errors.

## Token and cost implications

No model, embedding, network, or provider call is added. A verified transfer avoids replaying
personal transcripts or re-extracting already reviewed episodic state.

## Dependency and licensing implications

No dependency is added. The implementation and fixtures are original Mnemo work.

## Reversal or migration strategy

No schema migration is introduced. Removing the service leaves existing canonical target objects
governed by their normal correction, retention, and deletion operations.

## Verification

- Reference tests cover deterministic rebasing, exact counts and hashes, idempotent replay,
  conflicting-target rejection, lifecycle rejection, sanitized interruption, and retry convergence.
- A real PostgreSQL test imports a SQLite bundle, verifies restart-stable target counts and digest,
  proves exact retry, and rejects a private-project viewer.
